# 粉丝与关注列表首页缓存

[社交模块](design.md) · [数据库与写入事务](database.md#列表版本表与迁移) · [接口兼容](api.md#首页缓存接入)

已实现并通过本地验收，缓存读取默认关闭。CreatorHub 的两个列表需要按关注时间和 ID 排序，首页使用 ZSet。MySQL 持有关系与版本，Redis 保存可重建的快照。关系投影的参考见[黑马点评课程](https://www.bilibili.com/list/ml2653244374?bvid=BV1cr4y1671t&oid=766995956)。

## Key、字段和过期策略

| 项目 | 设计 |
| --- | --- |
| 粉丝列表 | `creatorhub:social:follow:v1:<ownerId>:followers:<revision>` |
| 关注列表 | `creatorhub:social:follow:v1:<ownerId>:following:<revision>` |
| 容量 | 每个 key 最多保存前 51 条关系，覆盖任意合法 `limit` 和下一页判断 |
| ZSet 分数 | 关注建立时间转成 UTC 毫秒时间戳 |
| ZSet 成员 | 对端 ID 左补零至 19 位的十进制字符串；读出后去掉补位 |
| 空首页 | ZSet 只存保留成员 `__empty__`，分数为 `0`。该标记不能与关系成员并存 |
| TTL | 首测建议 60 秒，加 0–30 秒随机抖动。缓存命中不延长 TTL |

`ownerId` 来自会话，方向取自接口，`revision` 来自 MySQL。两个方向的 ZSet 均只投影对端 ID 和关注时间。昵称按本页 ID 批量读取，因此修改昵称无需使已有列表缓存失效。

使用 `ZRANGE key 0 <limit> REV WITHSCORES`，终点包含在范围内，最多得到 `limit + 1` 项。同分数时按成员字节序倒序，固定宽度的 ID 编码与 MySQL 的对端 ID 数值倒序一致。ID 在 Java 中按整数或字符串处理，不经过浮点数转换。正常空标记与未命中分别返回空页和触发回源。[Redis ZRANGE](https://redis.io/docs/latest/commands/zrange/) · [Redis ZSet 同分数排序](https://redis.io/docs/latest/commands/zadd/)

## 首页读取与回填

1. Controller 校验会话、方向及分页参数。有游标则直接执行原 MySQL 分页。首页缓存开关打开时，从 MySQL 主库点查当前账号与方向的版本，按该版本读 Redis。
2. 未命中时，由 `creatorhub-core` 在[同一只读快照](database.md#缓存回源查询)内重读版本和前 51 条关系。回填 key 采用此次快照读出的版本。事务结束后执行 Redis 回填，缩短数据库事务占用时间。
3. Lua 在单 key 上完成条件回填。先校验 TTL 和负载，包含条数、格式及空标记规则。key 已存在则直接结束。缺失时一次写入整组 ZSet 成员，再设置过期时间。这样并发读取看见完整的首页或空页。命中和重复回填都不延长过期时间。
4. 回源请求使用本次快照组装结果。缓存与回源共用裁剪、批量读昵称和游标生成规则。若结果有 `limit + 1` 条，截去最后一条，使用实际返回的末项生成游标。

若读缓存超时、key 类型错误或返回数据无法解析，则从 MySQL 读取该页。回填失败时仍可返回已查到的 MySQL 结果。业务 Redis 异常在社交模块内处理，并记录超时、格式错误或回填失败。会话存储不可用仍遵循[身份模块错误约定](../identity/api.md#会话与错误约定)。业务缓存关闭时，首页直接走原 MySQL 查询。

## 延迟回填与关系隔离

假设 A 关注了 B，B 的粉丝列表版本为 `7`。请求①读到快照「版本 `7`，粉丝含 A」，随后暂停。A 取关 B，在同一事务删除关系并把 B 的粉丝版本推进到 `8`。这时请求①即使恢复并回填，也只会写入 `followers:7`。请求②在取关成功后开始，从主库读到版本 `8`，只会走版本 `8` 的缓存或回源快照。旧 key 靠 TTL 回收。

这个保证适用于关系变更提交后开始的请求。执行期间与提交重叠的请求可以返回它已取得的快照，跨页保持现有实时查询语义。所有回源 SQL 都以当前登录用户为列表所有者，游标只作为时间和 ID 的分页边界。两个账号或两个方向之间没有共享的首页 key。

## 热点重建与上线

首版使用现有 Redis 客户端与 Lua。Lua 协调同一个 key 的写入，多个缓存未命中请求仍可能各自查询 MySQL。若压测发现同账号、同方向、同版本的并发冷读造成大量重复回源，再引入 Redisson。锁按这三个维度划分，获锁后重查缓存，等待超时回源。频繁关注造成的版本行竞争单独测量。

1. 应用 V6，升级所有关系写入实例。缓存关闭期间，新应用仍在关系写事务内推进版本。
2. 确认所有写入实例均维护版本后，按目标环境数据做对照压测。仅在确认收益时，通过 `CREATORHUB_FOLLOW_CACHE_ENABLED=true` 启用缓存读取。
3. 如需回退，先关闭缓存读取。若回退期间旧应用写过关系，后续重新启用前为所有实例切换 key 命名空间，例如 `v1` 改为 `v2`。让旧缓存自然过期。

业务 Redis 使用独立连接和超时。可设置 `CREATORHUB_FOLLOW_CACHE_HOST` 和 `CREATORHUB_FOLLOW_CACHE_PORT`，默认跟随会话 Redis 地址。命令和连接预算由 `CREATORHUB_FOLLOW_CACHE_TIMEOUT` 配置，默认 `100ms`。缓存命名空间由 `CREATORHUB_FOLLOW_CACHE_NAMESPACE` 配置，默认 `v1`。

将 `com.creatorhub.core.social.service` 日志级别设为 `DEBUG`，可统计首页命中、未命中、快照回源、缓存读取异常和回填失败。日志记录方向和异常类型。

## 本地验收场景

| 场景 | 可观察结果 |
| --- | --- |
| V5 到 V6 | 原关系数据和索引保留，无版本行的已有账号可按版本 0 查询和回填 |
| 重复关注与取关 | 实际变更只推进 A 的关注和 B 的粉丝版本；幂等重试保留原关注时间及版本；反向关系独立 |
| 事务回滚 | 人为触发版本写入失败，确认关系和两个版本均未提交 |
| 延迟回填 | 暂停旧快照回填，取关成功后放行旧请求，新请求仍只使用新版本 |
| 并发回填和空缓存 | 同一版本只产生一份完整的列表或空标记，key 已设置 TTL，重复命中不会续期 |
| 排序与分页 | 同毫秒含大 ID 的关系在冷热路径结果一致；固定数据下首页接续页无重复遗漏；覆盖 `limit=1、20、50` |
| 账号隔离与昵称更新 | 更换账户后重新按会话查列表；跨账号游标不改变归属；改昵称后命中旧关系缓存仍能读到新昵称 |
| Redis 故障 | 会话健康、业务 Redis 故障时回源正确；会话故障时仍返回 `503` |
| 性能对照 | 用相同数据比较纯 MySQL、Redis 热读、并发冷读及多人关注同一作者，记录读写 P95、MySQL 查询次数、扫描行数和版本行锁等待 |

### 本地性能对照

隔离 MySQL、会话 Redis 与业务 Redis。首页样本为同一个账号的 64 条同毫秒粉丝数据，使用默认页长，16 并发。热读与纯 MySQL 各预热后测 160 次 HTTP 请求，冷读从空 key 测 16 次。SQL 次数和扫描行数取 MySQL Performance Schema 的相关语句聚合差值。

| 路径 | P95 | SQL 次数 | 扫描行数 | 缓存命中 |
| --- | ---: | ---: | ---: | ---: |
| 纯 MySQL | 17.01 ms | 158 | 6720 | 未使用 |
| Redis 热读 | 19.49 ms | 297 | 3451 | 160/160 |
| Redis 并发冷读 | 40.46 ms | 64 | 1184 | 0/16 |

关系写入使用 16 个不同账号并发操作同一个目标。V5 的关注和取关 P95 分别为 20.44 ms、19.90 ms。V6 分别为 72.05 ms、48.61 ms。V6 两轮各观测到 15 次 InnoDB 行锁等待，累计 363 ms、223 ms。此指标为隔离 MySQL 实例全局增量。V6 写入事务即使关闭缓存读取也会维护版本。

这组样本中，热读减少扫描行数，但增加 SQL 次数，P95 上升。因此保留默认关闭。并发冷读共触发 16 次快照查询，Lua 仍只回填一个 ZSet。是否引入 Redisson 留待更高复用率的负载下重新评估。
