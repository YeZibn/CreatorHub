## Context

现有草稿与关注已经独立交付。内容表的 V2 约束只允许 `DRAFT`，现有四个草稿 API 按作者和状态过滤。当前 Canal 白名单仅包含 `cdc_smoke_probe`。业务范围见[提案](proposal.md)，接口行为见[增量规格](specs/article-publishing/spec.md)。

## Goals / Non-Goals

- 作者完成一次原子状态转换，登录读者在提交后即可按原 ID 阅读。
- 复用现有内容表和授权边界。本阶段的部署独立于 Feed、Kafka 消费者和缓存。

## Decisions

### 同一内容行承载两个状态

新增 Flyway V4，在 `content` 上增加可空的 UTC `published_at DATETIME(3)`，替换现有状态约束。约束要求 `DRAFT` 的发布时间为空，`PUBLISHED` 的发布时间非空。保留已有草稿、默认状态、主键和索引。沿用同一行也保留了草稿编辑时使用的身份与版本，避免建立发布记录映射。

### 发布事务与重试

Controller 取得认证上下文中的作者与请求版本。内容 Service 在短事务中按主键和作者查当前内容行，使用 `FOR UPDATE` 与草稿保存串行化。在 `DRAFT` 分支先检查版本，再用现有 Unicode 空白规则校验已保存的标题和正文。以 ID、作者、状态和版本作为更新条件，将状态设为 `PUBLISHED`，版本加一，同时写入 `published_at` 和 `updated_at`。响应使用更新后的记录，提交成功后才返回。

同一事务的当前读也处理重试。属于作者的记录已发布时，只有 `当前版本 - 1 = 请求版本` 返回同一发布结果，其他版本返回冲突。此判断依赖本阶段已发布记录无需再次改版。后续引入编辑、下架或重新发布前，应重新设计发布重试的识别依据。

### 阅读与消息边界

阅读走独立查询，使用主键和 `status = 'PUBLISHED'`，响应中仅包含阅读所需字段。登录用户的阅读权限不依赖关注。发布成功依赖数据库提交，Canal 白名单继续只包含验证表。Feed 阶段再定义独立的发布事件、受众计算、重试与回填规则。

## Risks / Trade-offs

- 草稿保存与发布竞争时，事务使一个写入先完成，另一个基于新状态与版本返回已有接口约定的错误。
- 客户端可能在提交后丢失响应，作者重发同一请求版本可取回首次发布时间和文章内容。
- MySQL 使用完整行镜像，保持业务表过滤，并用 Kafka 同分区验证标记证明 CDC 链路仍在工作。

## Migration Plan

先确认现有 Canal 白名单，再在 V3 库上验证 V4 已保留已有草稿和索引，最后启用发布与阅读接口。回退 API 前核对旧制品对 V4 迁移历史及已发布数据的兼容性，保留内容与发布记录。
