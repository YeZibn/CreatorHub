## Context

MySQL 的 `follow` 表已为关注和粉丝列表分别提供排序索引。现有游标包含方向、UTC 毫秒时间和对端 ID。Redis 已用于会话。详细定义见[社交数据库设计](../../../../docs/design/social/database.md#列表版本表与迁移)及[首页缓存设计](../../../../docs/design/social/cache.md)。

## Goals / Non-Goals

**Goals**

- 对同一账号、同一方向反复请求的首页复用关系快照。
- 保证关系变更提交后的读取和冷热路径的分页契约，并保留 MySQL 降级路径。
- 通过独立开关压测和上线。所有运行新版本的写入实例均维护关系版本。

**Non-Goals**

- 公开粉丝列表、共同关注、粉丝计数、推荐阅读、Feed 分发及 CDC 事件变更。
- 全列表缓存或对现有前端与 API 契约的调整。

## Decisions

1. **以关系事务推进两端版本。** Flyway V6 创建 `follow_list_revision(owner_id, direction, revision)`，主键为前两列。方向 `1` 表示关注，`2` 表示粉丝。缺行视为版本 0。A 关注或取关 B 时，只有关系实际写入才推进 `A/FOLLOWING` 和 `B/FOLLOWERS`，并固定版本行的更新顺序。关注先验证目标状态，联合主键冲突仅作为该关系的幂等重复处理，取关按删除行数判断。关系与版本同事务提交。版本化 key 使晚到的旧回填仍写到旧版本。
2. **只缓存有序首页。** Redis key 使用可配置的命名空间版本以及会话所有者、方向和关系版本。每个 ZSet 最多保存前 51 条关系，分数为 UTC 毫秒值，成员为左补零的 19 位对端 ID。放入一条专用空标记表示确认无关系。按照 `limit + 1` 读取和裁剪，复用原游标编码。续页走现有联合索引，单条关注状态走主键。两个方向都按当页用户 ID 批量获取昵称。
3. **使用同一数据库快照回填。** Controller 验证会话及原分页参数。Service 从主库查当前版本，再读 Redis。未命中时，在单个只读 `REPEATABLE READ` 事务的一致性读中重查版本和前 51 条关系。以快照查得的版本构造回填 key，事务结束后调用 Lua。脚本先校验参数，再在一个 key 上执行存在检查、整批写入和 TTL 设置。初始压测使用 60 秒加 0–30 秒抖动，命中不续期。
4. **在社交模块内处理业务缓存错误。** Redis 调用失败、数据无效时回源，回填失败时返回已获得的 MySQL 结果。资料缺失时可回退原带资料连接的 SQL。由独立预算控制业务缓存调用超时，避免影响会话存储错误的既有处理。统计命中、回源、超时和回填失败。
5. **按实际重复回源决定是否引入 Redisson。** 首版以 Lua 保证完整回填。若并发冷读确实引发大量重复 SQL，再单独设计按所有者、方向和关系版本划分的短时重建锁，锁等待超时则回源。热门作者写入竞争由压测单独评估。

## Risks / Trade-offs

- 热读仍查 MySQL 版本和昵称。用相同数据和并发比较纯 SQL、冷读和热读的 P95、SQL 数量与扫描行数。
- 列表版本行增加热点作者写入竞争。用多人同时关注及取关同一作者测量写入 P95 和锁等待。首版默认关闭缓存读取，基准数据支持后再启用。
- 每页仍为实时列表。与关系写入重叠的请求可能返回其已取得的快照。提交后开始的请求从主库读取新版本。

## Migration Plan

先从 V5 应用 V6。既有关系无需回填版本。部署期间关闭缓存读取，所有关系写入实例升级后再开启。回退时先关闭缓存，若期间有旧应用写关系，重新启用前为所有实例统一更换缓存命名空间。旧 key 随 TTL 到期，保留 Flyway 历史。
